# Руководство для агентов

Инструкция описывает метод работы, а не стек. Конкретику проекта - команду тестов, команду локального
выката, хостинг репозитория и его CLI, трекер задач, раскладку исходников - выясняй по самому репозиторию:
README, файл сборки, конфигурация CI, remote.

**MR** дальше по тексту - запрос на слияние ветки: merge request или pull request.

## Где лежат инструкции

Инструкции подключают к проекту сабмодулем в папке `agents` или плагином `hacode-skills` (скилы `build`,
`check`, `docs`, `ui`, `review`, `cleanup`). Пути в тексте (`modes/common.md`, `scripts/mr-reply.sh`)
отсчитываются от корня этой папки, а не от корня проекта. Подключено и то и другое - берём сабмодуль.

## Общие правила

Перед работой в любом режиме полностью прочитай [`modes/common.md`](modes/common.md).

## Режимы работы

- DOCS - изменение/дополнение документации
- BUILD - разработка фич, исправление багов, исправление комментариев в MR
- CHECK - аудит и поиск несоответствий
- UI - редизайн экрана, который выглядит сгенерированным (`modes/ui.md`)
- REVIEW - ревью кода в merge request (отдельный сабагент на каждый MR, `modes/review.md`)
- CLEANUP - удаление мусора после ребейзов/разработки/правок (без изменения поведения)

По умолчанию: BUILD. Инструкции режимов лежат в папке `modes` и применяются вместе с `modes/common.md`.

## Обращение к человеку

- При инициализации спроси имя человека, если не знаешь его.
- Всегда обращайся к человеку по имени.
- Забыл имя и тебе напомнили - перечитай инструкции целиком и сверься с ними: потерянное имя означает,
  что из виду упущено и остальное.

## Общий workflow

1. Основная ветка выбрана - создай отдельную: `fix/…`, `chore/…`, `docs/…` (имя от задачи не зависит).
2. Прочитай `modes/common.md` и инструкцию выбранного режима.
3. Прочитай все `README.md` в папке требований и в папке рабочего контекста, затем релевантные документы.
4. Сформируй или обнови контекст согласно инструкциям.
5. Обнови документацию, если пользователь попросил изменить поведение.
6. Выполни задачу.
7. Проверь соответствие документации.
8. Обнови контекст согласно инструкциям.
9. Сделай cleanup в соответствующем режиме.
10. Сделай коммит с осмысленным сообщением.
11. Запушь ветку в удалённый репозиторий.
12. Создай или обнови MR через CLI форжа - черновиком (см. «Коммиты и merge request»).
13. Запусти **MR-review-monitor** для MR, если ещё не запущен.
14. Заведи в MR тред с тест-планом (`modes/build.md` → «Тест-план в треде MR»).
15. В ответе человеку укажи ветку, коммит, ссылку на MR и выполненные проверки.
16. На каждый ревью-коммент ответь в треде: что изменили или почему делать не надо.

**MR-review-monitor** - фоновый процесс под инструментом `Monitor` (persistent): следит за комментами,
апрувами и отметками тест-плана на своих открытых MR и шлёт событие на каждое; событие отрабатывается
как BUILD-задача (`modes/build.md`). Свой скрипт на роль автора и на роль ревьюера. Чужие MR не трогаем.
При нескольких MR: план по комментам ведём в файле активной задачи; перед commit/push переключаемся на
ветку нужного MR.

Апрув пользователя перед коммитом/пушем не требуется. Чужие изменения в рабочем дереве - спроси человека,
коммитить ли их.

## Задача и MR

Первая строка описания MR - `Closes <KEY>` или `Related to <KEY>` (`ABC-123`, `PROJ-45`, `#123`). Задач
несколько - `Closes <KEY-1>, <KEY-2>`. Идентификатор оборачиваем ссылкой на задачу из трекера. `Closes`
ведёт задачу по статусам и закрывает по мержу, `Related to` только связывает. Комментарии и коммиты трекер
не читает - связь ставится описанием или заголовком MR. Если трекер понимает эти слова иначе - следуем его
правилам, место то же: первая строка описания.

Задачи нет - спроси владельца, заводить ли её, и жди ответа. MR без идентификатора допустим только после
явного «задачу не заводим».

## Коммиты и merge request

- Пишутся на английском.
- Заголовок + тело по существу, без планов по тестированию.
- Без подписи-генератора (никаких «Generated with …» и Co-Authored-By).
- Без GPG-подписи: коммитим с `--no-gpg-sign`.
- Описание коммита короче описания MR: заголовок + пара строк по сути.

MR открываем черновиком средствами CLI форжа (`glab mr create --draft`, `gh pr create --draft`); `Draft:` в
`--title` руками не добавляем. Черновик снимается, когда MR апрувнут, все треды закрыты и полный проход
CLEANUP + CHECK зелёный без правок (`glab mr update <iid> --ready`, `gh pr ready <n>`). Свои треды закрываем
сами. Мерж - право владельца.

**«Можно мержить» от человека - разрешение, а не готовность**: мержим только после апрувов, зелёного
пайплайна, закрытых тредов и проставленных галочек тест-плана.

**Апрув агент не ставит** - ни на своём MR, ни на чужом. Вывод ревью пишется в треды у строк; общий тред -
только когда замечаний нет (`modes/review.md`). Апрув и мерж - действия человека.
