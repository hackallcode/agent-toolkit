# Режим: CHECK

Аудит системы на соответствие.

Перед CHECK обязательно прочитай [`common.md`](common.md); нарушения общих правил входят в аудит.

## Правила

- проверить docs == код
- проверить код == context
- проверить пользовательские флоу
- проверить UX-спеки и таблицу покрытия для новых/изменённых экранов, если такие спеки в проекте есть:
  наличие спека и записи (либо записи в исключениях с причиной), а не зелёный прогон вне CI
- новые и изменённые экраны пройти по «Признакам слопа» из `modes/ui.md`
- находить нарушения `common.md` и инструкции соответствующего режима
- находить баги
- прогнать тесты проекта: любое падение фиксируется с командой и выводом
- проверить структурные ratchet-бюджеты: новые и выросшие записи требуют анализа владельца, улучшенные
  значения понижаются; механическое изменение бюджета ради зелёного теста - проблема
- сравнить architecture/source hygiene tests, budget и baseline файлы с parent commit: область измерения и
  исключения не расширены, проверки не ослаблены, новый baseline не скрывает нарушение из текущего diff без
  явного решения
- зелёные тесты - не доказательство отсутствия проблем: проверить docs, прямых владельцев, зависимости,
  транзакции, конкурентные границы, порядок внешних эффектов, отсутствие фасадов/forwarding/mixins для
  обхода метрик
- прогнать метрические гейты, если они есть в проекте: CRAP функции (сложность с поправкой на
  непокрытость) ниже порога проекта, ориентир - 10; структурные дубли выше порога похожести устранены;
  мутационное тестирование - непокрытое покрыто, выжившие мутанты убиты тестом или код под ними удалён
  как мёртвый
- в исправлении бага найти guard, который прячет падение вместо устранения причины; в коде - заглушённые
  проверки типов без причины (`common.md` → «Данные, типы и границы»)
- проверить доказательную ценность новых и изменённых тестов по `common.md`: названная реалистичная
  регрессия, независимый oracle, test double не проверяет собственную настройку
- проверить уровни тестов: wiring, repository, транзакции, конкурентность, сериализация - integration;
  пользовательский межслойный flow - e2e (если unit-тесты дублируют mocks и production-ветвление)
- найти повторяющиеся happy-path тесты, механические snapshots/goldens, проверки несущественного call order
  и test-only копии production-алгоритма
- для каждого split проверить owner graph и живые imports: старый путь отсутствует, consumers идут прямо к
  owner, нет facade/re-export/forwarder/delegating shell/MRO-mixin/file-only fragments с общим состоянием
- не обращать внимания на лёгкие недочёты, которые ни на что не влияют
