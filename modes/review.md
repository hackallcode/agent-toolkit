# Режим: REVIEW

Аудит merge request на качество кода и соответствие требованиям.

Перед REVIEW обязательно прочитай [`common.md`](common.md).

## Правила

- проверить код в merge request, используя режим CHECK
- задавать вопросы в местах, где есть другие варианты реализации со своими преимуществами
- все результаты публиковать комментариями в режиме комментирования кода

## Сабагент на MR

Ревью MR ведёт отдельный сабагент. На свой MR он заводится сам после зелёного CI
(`modes/build.md` → «Пайплайн»).

- **Один MR - один сабагент.** К тому же MR возвращаемся тем же (`SendMessage` по имени); два MR в одном
  сабагенте не смешиваются.
- **На чужой MR монитор ревьюера поднимает основной агент**: `scripts/mr-review-watch.py --mr <iid>`.
  Приходят комменты и `NEW COMMIT <sha>`; событие передаётся сабагенту того же MR.
- **На своём MR монитора нет** - с сабагентом говорим напрямую.
- **Сабагент пишет прямо в MR.** Инлайн-тред - `scripts/mr-reply.sh <mr> --line <path>:<line> [файл]`
  (на диапазон - `<path>:<from>-<to>`), ответ в тред - тот же скрипт с id треда. Замечание длиннее 1500
  символов режем или называем причину в `MR_ALLOW_LONG`.
- **У каждого пишущего свой writer-тег.** Заметка считается нашей по записи `<id> <тег>` или по нашему
  маркеру в конце заметки. Сабагенту задаём `MR_AGENT_TAG=review-mr-<iid>`.
- **Апрув не ставим, итог не пишем.** Вывод ревью - треды у строк; после фикса - ответ в том же треде и резолв
  своего треда. Общий тред открываем только когда замечаний нет: одна строка - коммит, на котором смотрели,
  и что проверить не удалось, если такое есть.
- **Проверяем фикс, а не отчёт автора**: перечитываем дифф, прогоняем тесты, мутацией убеждаемся, что новый
  тест ловит регрессию. Свой тред резолвим только после этого.
- **Сабагента удаляем не раньше, чем MR смержен или закрыт.**
