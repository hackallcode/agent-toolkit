# Общие правила разработки

Обязательны во всех режимах: BUILD, CLEANUP, CHECK, DOCS, UI, REVIEW. Файлы режимов дополняют их, но не
отменяют. Перед работой прочитай этот файл целиком.

Правила не зависят от языка, фреймворка и хостинга. Конкретика проекта - команда тестов, команда локального
выката, раскладка исходников, набор архитектурных проверок - берётся из самого репозитория. Требования живут
в `docs/**`, рабочий контекст - в `context/**`; называются иначе - подставляй раскладку проекта.

## Источник истины и изменение поведения

Приоритет источников:

1. `docs/**` - требования к продукту, UX, runtime, безопасности и эксплуатации.
2. Код и тесты - фактическая реализация.
3. `context/**` - рабочее состояние и временные планы, но не требования.

- Прочитай все `README.md` в `docs/**` и `context/**`, затем релевантные документы. Перед изменением любой
  папки проверь её локальные `README.md` и `AGENTS.md` и инструкции в родительских папках.
- Код расходится с `docs/**` - правильна документация, если задача явно не меняет требование.
- Не придумывай отсутствующее поведение и не меняй молча пользовательскую логику: новое или изменённое
  поведение описывается в `docs/**`.
- Архитектурный рефакторинг сохраняет документированное поведение и не смешивается с продуктовым изменением,
  миграцией схемы или изменением смысла запросов. Изменение продукта, схемы или смысла запросов оформляется
  отдельным MR с отдельной проверкой документации, миграции и отката или обратной совместимости.
- Переименование затрагивает и строки за границей процесса: имена в чужом API, ключи в хранилище, значения в
  базе, переменные окружения, задачи планировщика, объекты инфраструктуры. Перечисли их в описании MR с
  решением по каждой (переименовать с миграцией или оставить) и проверяй по внешнему источнику - ответу
  сервиса, содержимому таблицы, развёрнутой конфигурации.
- В `docs/**` пишется только требование: что система делает, чего не делает, что видит пользователь.
  Обоснование - в commit message и описании MR.
- Требование неясно - не додумывай: задай вопрос или предложи изменение документации.

## Рабочий контекст

- Состояние реализации - в `context/implementation-status.md`.
- План активной BUILD-задачи - в `context/current-task.md`; удаляется после выполнения или перед новой
  задачей.
- Баги, решения, риски и проверки текущей задачи пишутся в `context/current-task.md`.
- Долговременные выводы переносятся в `context/implementation-status.md`, продуктовые решения - в `docs/**`.

## Направление зависимостей

```text
точки входа и каналы
        -> прикладные сервисы и сценарии
        -> чистый домен и узкие контракты

инфраструктурные адаптеры реализуют контракты
место сборки приложения связывает сервисы с адаптерами
```

- Домен импортирует только стандартную библиотеку и собственные модули без ввода-вывода. Объекты данных и
  правила домена принадлежат домену или использующему их сервису, а не адаптеру базы данных.
- Прикладной сервис не импортирует конкретную реализацию хранилища, широкий универсальный интерфейс или
  нетипизированную заглушку. Сервис объявляет минимальный контракт (`Protocol`, `interface`, trait) ровно из
  тех операций, которые вызывает. Ошибка «зависимость не передана / не реализует метод» - на этапе сборки;
  динамическая проверка наличия метода запрещена.
- Корневой модуль пакета (`__init__.py`, `index`, `mod`) по умолчанию ничего не загружает. Внутренний код
  импортирует символ из модуля, где он объявлен. Повторный экспорт - только для подтверждённого внешнего API
  и без работы при импорте.
- Импорт модуля не меняет переменные окружения и глобальное состояние, не обращается к сети, не грузит
  модель, не запускает поток, listener или server. Реестр создаётся явно и после сборки не меняется.
  Созданием и остановкой ресурсов владеет место сборки приложения.
- Цикл не прячется локальным или динамическим импортом. Импорт «только для проверки типов» - только для
  зависимости, нужной исключительно ей; локальный импорт - только на границе необязательной зависимости.
  Импорты проверяются в отдельном чистом процессе.
- Helper, renderer, label, pagination и правило живут рядом с кодом, за смысл которого отвечают. Адаптер не
  импортирует канал доставки и не создаёт приложение или другой адаптер. Конкретные реализации связываются
  только в месте сборки.

## Данные, типы и границы

- Сначала форма данных, потом логика. Домен описан структурой, в которой недопустимое состояние не
  записать: перечисление вместо строки, отдельный тип вместо флага-комбинации.
- Внешние данные разбираются и проверяются один раз - там, где входят в систему; внутри им доверяют, без
  повторных проверок по слоям. Бизнес-правило - чистая функция без ввода-вывода.
- Компилятор и проверку типов не глушат ради зелёной сборки (`# type: ignore`, `any`, `@ts-ignore`,
  `unsafe`, `nolint`); исключение - с причиной в одну строку там же.
- Одно решение живёт в одном месте: константа, правило или маппинг не дублируются по модулям.

## Владение ресурсами и конкурентность

- У каждого pool, client, listener, server, executor и worker один явный владелец. close/drain/shutdown/join
  ограничены по времени. Bind и проверка конфигурации - до запуска рабочих потоков; ошибка частичной сборки
  закрывает уже созданные ресурсы.
- Конкурентная работа с базой - явные pool и session, короткие атомарные транзакции; при необходимости -
  блокировка строки, lease, token владельца, CAS против записи устаревшего worker.
- Вызов внешней системы (сеть, канал доставки, платежи, очередь, файловая система) - только после commit и с
  сохраняемым контрактом повтора или сверки результата.
- Операция идемпотентна: повторный запуск или перезапуск после падения на середине приводит к тому же
  состоянию.
- Изменяемое состояние, которое не обязано быть общим, у каждого своё. Обязано - один писатель, и это
  закреплено структурой (владелец, очередь, lock), а не договорённостью.
- Регрессионный тест использует настоящий адаптер и независимые соединения. Тестовая реализация повторяет те
  же результаты, ограничения и ошибки, а не упрощает контракт.

## Проверка архитектурного изменения

Перед завершением архитектурного рефакторинга:

- Определи, где живёт изменяемый код, за какую ответственность отвечает и в какую сторону разрешена
  зависимость; где сервис связывается с конкретным адаптером.
- Перечисли требования из `docs/**`, которые должны остаться без изменений, и проверь тесты, фиксирующие
  поведение до переноса.
- Объяви в контракте сервиса ровно те методы хранилища, которые он вызывает; убери конкретную реализацию,
  широкий интерфейс, заглушку и обходы через динамическую проверку. Ошибка сборки - немедленная.
- Запусти импорт в отдельном чистом процессе: корневой модуль инертен, цикл не спрятан, импорт не создаёт
  ресурс и не выполняет работу.
- Проверь по каждому ресурсу, кто создаёт и закрывает; откат частичного старта; ограниченные
  shutdown/drain/join; bind до рабочих потоков.
- Для конкурентного кода - детерминированный тест настоящего адаптера с независимыми соединениями: короткая
  транзакция, защита от устаревшего владельца, внешний вызов после commit, одинаковое поведение настоящего
  адаптера и тестовой реализации.
- Запусти архитектурные проверки запрещённых зависимостей, циклов и тяжёлых импортов. Изменение не добавляет
  обёртку, второй путь к тому же поведению или механическое деление на обёртки/mixins; улучшение одной
  метрики не скрывает нарушение в другой.
- Прогони структурные ratchet-проверки проекта, если есть: новая задолженность не добавляется, улучшенные
  значения сразу понижаются в бюджете. Повышение бюджета - только после явного ревью владельца.
- Зелёные тесты не доказывают качество архитектуры: отдельно проверь соответствие `docs/**`, владельцев,
  зависимостей, транзакционные и конкурентные границы, порядок внешних эффектов и отсутствие обхода
  ratchet-проверок фасадом, forwarding-методом, mixin или переносом строк.

## Тексты, комментарии и чистота кода

- В текстах и коде - обычный дефис `-`; длинные тире не пишутся.
- В комментариях и docstring нет путей `docs/**` и `context/**`.
- **Нет change-log.** Комментарий описывает, как код устроен сейчас. Формулировки через прошлое («раньше было
  так», «больше не принимаем») и номера MR и коммитов - в commit message.
- Комментариев мало: только причина неочевидного решения, ограничение или workaround. Одна строка; длинное
  объяснение - в документации или commit message. Правило одинаково для production-кода, тестов и
  конфигурации (CI, манифесты, сборочные файлы).
- Комментарии и docstring - по-английски, как и сообщения коммитов. Пользовательские тексты локализуются по
  правилам проекта: исходная строка оборачивается в функцию перевода, перевод добавляется в каталог для
  каждого языка; значения пользователя, числа и имена в ключ перевода не входят; заимствование не
  используется, если есть понятный родной вариант.
- На каждом затронутом экране перечитай тексты и кнопки: без служебного жаргона, дублей и промежуточных
  формулировок. Кнопка называется по результату действия; ссылка оформляется кнопкой и поясняется словами.
- Если в проекте есть UX-спеки или приёмочные сценарии, новый или изменённый экран обновляет спек и получает
  строку в таблице покрытия либо запись в разделе исключений с причиной.

### Обязательная уборка после задачи

Перед завершением задачи убери всё лишнее, появившееся из-за неё:

- мёртвый код и неиспользуемые импорты, переменные, функции, классы, ветки, параметры;
- недостижимые условия, закомментированный код, отладочные `print` и логи;
- совместимые обёртки, алиасы, повторные экспорты и параметры совместимости без живых пользователей;
- временные обходы и `TODO`/`HACK`/`FIXME` с устранённой причиной;
- дубли и параллельные реализации одного поведения;
- комментарии о том, как код работал раньше, и ссылки на номера MR, коммитов, тредов;
- пути `docs/**` и `context/**` в комментариях и docstring;
- осиротевшие тесты, fixtures и helpers;
- маркеры конфликтов, повторённые блоки и осиротевшие файлы после rebase;
- пустые секции, висячие заголовки, оборванные списки в документации;
- выполненные задачи и протухшие записи в `context/**`.

Непонятно, нужна ли старая совместимая конструкция, - проверь живые вызовы и документацию: без
подтверждённого использования удаляй. Не удаляются публичный интерфейс с живыми вызовами из кода или тестов
и поведение из `docs/**`.

## Декомпозиция файлов и пакетов

Размер - сигнал, а не цель. Дели файл или папку, только если она одновременно велика и содержит несколько
самостоятельных ответственностей.

### Production-файлы

- Меньше 200 строк - оставь как есть.
- 200-350 строк - норма; дели только при нескольких независимых обязанностях.
- Больше 350 строк - кандидат на разделение по экрану, домену, стадии обработки или владельцу lifecycle.
- Больше 500 строк - почти всегда разделяй, кроме цельного pipeline, state machine, composition wiring или
  описания схемы данных.
- Новая самостоятельная «глава» каждые ~150 строк - дополнительный сигнал разделить.
- Запрещены произвольные обёртки, модули `part2`, mixins без самостоятельной ответственности.
- Разделение завершено, только если у каждого нового модуля есть semantic или lifecycle owner, consumers
  импортируют его напрямую, а старый путь удалён. Facade, re-export, forwarding method, delegating shell,
  MRO-mixin и compatibility wrapper декомпозицией не считаются.
- Не дели цельный worker с одним циклом или файл с одним связным классом только из-за длины; если после
  разделения одно состояние передаётся через несколько уровней параметров - разделение хуже цельного файла.

### Пакеты

- ~10 файлов в папке с единой ответственностью - сигнал выделить подпакет.
- Общий префикс в именах и минимум три связанных файла - основание для подпакета; два файла остаются в
  текущей папке.
- В подпакете главный класс живёт в явно названном модуле владельца (`service`, `client`, `plane`); остальные
  файлы отвечают каждый за одну часть.
- Новый корневой модуль пакета инертен и по возможности пуст. Публичный package API меняется только отдельным
  решением; навигационные docstring и повторные экспорты не добавляются.
- Внутренний код импортирует символ из модуля, где он объявлен; публичный повторный экспорт - только для
  подтверждённого внешнего API.
- Связная сборка приложения и описание схемы данных остаются цельными.

### Mixins

- Mixin - только для самостоятельной ответственности внутри одного большого класса; лежат рядом с главным
  классом, каждый отвечает за один домен.
- Stub-методы в mixin запрещены. Типы атрибутов задаются контрактом использующего сервиса.
- Внутрипакетный код импортирует mixin из его модуля; публичный повторный экспорт - по общему правилу
  инертного корневого модуля.

### Тесты

- Каждый тест защищает наблюдаемый контракт или неочевидный инвариант и имеет независимый oracle и названную
  реалистичную регрессию, при которой упадёт. Покрытие строк и число тестов - не цель.
- Бессмысленный тест: повторяет production-алгоритм в expected, проверяет возвращённое mock-ом значение,
  фиксирует несущественные детали реализации, не отличает рабочую реализацию от реалистично сломанной;
  тривиальные getter/dataclass/constructor без инварианта, механически обновляемые snapshot/golden без
  независимого источника истины, одинаковые сценарии с несущественно разными данными. Быстрая проба: тест
  прошёл бы, если бы каждая функция под ним возвращала пустое значение, - тест удаляется.
- Тест вызывает код так, как его вызывает пользователь кода, и проверяет то, что тот увидит.
- Не проверяй порядок внутренних вызовов, форму локального кода, имя alias или точный private helper, если это
  не контракт транзакции, lifecycle, конкурентности, сериализации, внешнего эффекта или архитектурной границы.
- Expected не вычисляется production-helper-ом или копией его ветвления: явные примеры из требований,
  независимо рассчитанные значения, реальный adapter или наблюдаемый результат на границе системы.
- Уровень - минимальный, видящий риск. Unit - чистая детерминированная политика и преобразования.
  Integration - wiring, repository, транзакции, CAS, locks, сериализация, взаимодействие owners/adapters.
  E2E - пользовательский сценарий через entrypoint, канал и composition; один сфокусированный e2e может
  заменить дублирующие проверки каждого слоя.
- При рефакторинге сначала добавь characterization на самой узкой наблюдаемой границе; после переноса оставь
  минимальный непересекающийся набор - отдельные тесты защищают разные риски.
- Redundant test удаляется после указания более сильного теста того же контракта; facade, forwarding wrapper
  и test-only duplicate production logic более сильным покрытием не считаются.
- Структура тестов повторяет структуру исходников; общего файла-сборника тестов проекта нет - раскладка по
  доменам.
- Имя файла: `test_<домен>_<сценарий>` в стиле языка; один файл - одна узкая тема (lifecycle, callbacks,
  edge cases).
- Меньше 300 строк - норма; 300-600 - дели при независимых сценариях; больше 600 - почти всегда дели по
  сценариям и владельцам fixtures.
- Общие factories, fixtures и builders живут в общей точке своей области, а не копируются по файлам.
- В test case - только отличия от значений по умолчанию; видно условие, действие и ожидаемый результат.
- Большой тестовый файл - повод проверить и production-код: область, возможно, требует отдельного пакета.

### Структурные ratchet-бюджеты

Правила применяются к автоматическим структурным проверкам проекта (число файлов, длина и ветвление функций,
число методов, неинертные package roots, private imports); нет проверок - те же требования проверяются
глазами в CHECK.

- Порог - сигнал для ревью, а не цель. Запрещено обходить его пустым фасадом, forwarding-классом, split-only
  mixin, модулем `part2`, переименованием private API или переносом связного кода без нового владельца.
- Существующее превышение хранится как точный no-growth бюджет; значение уменьшилось или владелец исчез -
  бюджет понижается или удаляется в том же изменении.
- Обоснованное превышение (цельный pipeline, state machine, composition owner, схема данных) - в diff
  выносится точное текущее значение, в описании MR - ответственность владельца.
- CHECK оценивает все метрики вместе: локальное улучшение не создаёт широкую зависимость, дублирование,
  цикл, новый публичный API или скрытый service locator.
