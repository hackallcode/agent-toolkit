# Разработка тулкита

## Что где лежит

```text
AGENTS.md            общий гайд: workflow, режимы, правила задач, коммитов и MR
CLAUDE.md            симлинк на AGENTS.md
modes/
  common.md          общие правила, обязательны во всех режимах
  build.md           режим BUILD
  check.md           режим CHECK
  docs.md            режим DOCS
  ui.md              режим UI
  review.md          режим REVIEW
  cleanup.md         режим CLEANUP
scripts/             GitLab-скрипты инструкций (мониторы MR, ответы в треды) и сборка скилов
skills/              собирается из modes/; в основной ветке не хранится, публикуется CI в ветку dist
tests/               тесты скриптов: отказы scripts/mr-reply.sh, версия и frontmatter сборки скилов (pytest)
templates/           заготовки для проекта-потребителя (AGENTS.md, docs/, context/)
```

Пути внутри инструкций (`modes/common.md`, `scripts/mr-reply.sh`) указаны **относительно корня этого
репозитория** - и когда он подключён сабмодулем, и когда установлен плагином.

## Сборка скилов

Меняем `modes/**` - `skills/**` собирается из них, правка собранного затирается следующей сборкой.
Тело режима становится `SKILL.md`, а `common.md` копируется рядом с ним: так скилл самодостаточен, агент
читает его файлы по соседству, а не по пути в корень плагина, который в момент чтения ему неизвестен.

```
make skills/build     собрать skills/** локально
make skills/clean     удалить собранное
make skills/local     поставить плагин из этого клона, а не из dist
```

`make skills/local` нужен, чтобы проверить правки режимов до пуша: он ставит marketplace из каталога
клона со свежесобранными скилами. Снять - тем же `make skills/delete`.

## Тесты

```
python -m pytest tests -q
```

Нужны `jq`, `awk`, `bash` и `python3` - `scripts/mr-reply.sh` читает ими ответы, разбирает чеклист
и считает маркер агента. Один тест изображает awk без интервальных выражений и требует `gawk`,
без него он пропускается. Проверка frontmatter скилов требует `pyyaml`, без него тоже пропускается.

## Ветка `dist`

`dist` - это основная ветка плюс собранный `skills/**`, её каждый раз переписывает джоба
`publish-skills` (`.github/workflows/ci.yml`). Руками в неё не коммитим.

### Версия плагина

`claude plugin update` и `codex plugin marketplace upgrade` ставят новую сборку, только если сменилась
версия в `plugin.json`, поэтому у каждой сборки `dist` она своя: `<major>.<minor>.<patch>`, где
`major.minor` берутся из `.claude-plugin/plugin.json` и `.codex-plugin/plugin.json`, а `patch` - число
коммитов основной ветки (`git rev-list --count --first-parent HEAD`). Одна ревизия всегда даёт одну
версию, а каждый мерж в основную ветку её увеличивает. Проставляет её `scripts/build-skills.py
--stamp-version` в обоих манифестах сразу, так что версии Claude- и Codex-плагина совпадают.

В основной ветке patch остаётся `0`: его перетирает сборка. `major.minor` поднимаем руками, в обоих
манифестах одинаково, иначе сборка откажется. На неглубоком клоне она тоже откажется: счёт коммитов
там обрезан, и версия поехала бы назад, поэтому джоба публикации клонирует историю целиком
(`fetch-depth: 0`).

Проверить публикацию до мержа: ручной запуск workflow с галкой `publish`, а вход `dist_branch`
уводит прогон на другую ветку, чтобы не трогать боевую.

```
gh workflow run ci.yml --ref <ветка> -f publish=true -f dist_branch=dist-test
```

### Токен публикации

Джобе нужны права на запись в репозиторий, и GitHub Actions выдаёт их сам: `GITHUB_TOKEN` с
`permissions: contents: write` пушит в ветки того же репозитория, отдельный PAT заводить не нужно.
Ограничение одно: пуш от `GITHUB_TOKEN` не запускает новых workflow, поэтому после публикации `dist`
пайплайн по ней не побежит - проверок у ветки нет и не надо.

Коммитера подписывают переменные `SKILLS_PUBLISH_NAME` и `SKILLS_PUBLISH_EMAIL` (Settings →
Secrets and variables → Actions → Variables); без них коммит пишет `github-actions[bot]`.

Если ветку `dist` защитите, добавьте исключение для `github-actions[bot]` (или для джобы) в правилах
этой ветки, иначе публикация будет отлетать.
